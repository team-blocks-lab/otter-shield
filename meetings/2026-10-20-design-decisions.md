## 3. M2 독일 본사·보안 비교

- M1과 같은 업무 서버 10대·직원 PC 6대·관리 PC 2대·L2 스위치 10대 구성으로 설계합니다. 32GB PC의 실제 동시 가동 범위는 양국을 같은 규모로 단계 조절합니다.
- 한국과 같은 사내 게시판 코드를 사용하고 독일 DB·계정·환경설정은 분리합니다. 같은 구조이지만 IP 대역은 중복하지 않습니다.
- AS-IS는 업무 정상 동작과 원본 로그를 확보하고, TO-BE에서 독일 전용 Wazuh 서버·독일 Agent·선정한 Active Response(자동 대응)를 적용합니다.
- Wazuh는 독일 내부만 감시합니다. 다른 망의 기존 M2 Agent 등록·Syslog 송신·허용 규칙·라우트·관리 중계 의존성은 모두 제거 대상으로 대조합니다.
- Wazuh는 업무 패킷이 통과하는 인라인 장비가 아닙니다. 로그 탐지·자동 대응·실제 차단을 각각 검증합니다.
- 한국·독일 비교는 OS·앱·계정 정책·시험 횟수·간격·UTM의 시험용 SSH 허용 조건을 맞춥니다. M1의 SSH 차단 시나리오와 별도 스냅샷을 사용합니다.

## 4. 보안 구성·시나리오

M2·M3의 **Suricata 구성과 관련 시나리오를 설계에서 전부 제외**합니다. 이 결정은 실제 VM 삭제·설정 해제 완료를 뜻하지 않습니다.

| 번호 | 승인된 격리 시험 | 개선 후 확인 |
|---|---|---|
| S01 M1 | 직원→본사 WAS SSH 관리 접근 | UTM 차단·관리자 정상 접속 |
| S02 M2 | 독일 직원 시험 PC→독일 WAS 반복 SSH 인증 실패 | Wazuh 경보·선정 자동 대응·차단 해제·관리자 정상 접속 |
| S03 M3 | M1 직원 시험 PC→K8s 관리 API | UTM 접근 제한·승인 관리자 정상. 포트 도달과 인증 우회는 구분 |
| S04 M4 | 비인가 시험 계정의 가짜 백업 파일 읽기 | 파일 권한 거부·읽기 감사·정상 백업/복원 |
| S05 M5 | 캐나다 직원→한국–캐나다 VPN·M1→M3 격리 Test DB | UTM3 직접 DB 접근 차단·정상 웹 업무 유지 |

S05는 종전 웹 IPS 시험을 대체합니다. 운영 DB·AWS RDS를 취약하게 만들지 않고 가짜 데이터·읽기 전용 시험 계정만 사용합니다. 각 망의 비독일 로그는 현지 기술서·원본 증거로 관리합니다.

## 5. 망 분리·주소·환경 설정

- M1·M2의 DMZ·SERVER·ADMIN은 독립 VMnet·UTM 포트, 직원·공통 구간만 VLAN trunk를 사용합니다. M3·M4·M5의 독립 VMnet에 불필요한 VLAN 번호를 붙이지 않습니다.
- UTM은 **UTM(Sophos UTM 9)**으로 표기합니다. 사용자 표기 9.0 외 정확한 build·라이선스는 구축 시 확인합니다.
- 기존 M1·M3·M4·M5 주소 계획은 유지하고, 독일은 중복 없는 별도 대역으로 설계합니다. 세부 IP 배정표는 팀 공유 기술서에서 관리하며 실제 교실 경계 IP는 확인 후 확정합니다.
- 한국–독일, 한국 본사–백업·DR, 한국–캐나다, 한국 서비스–백업·DR VPN을 구분합니다. Topology에는 연결 대상 이름을 사용합니다.
- 각 망의 NIC/MAC/VMnet·게이트웨이·반환 경로·NAT 예외·DNS·시간 동기화·접근 권한·로그·복원 기준을 함께 기록합니다.

## 6. 개발·CI/CD·문서 운영

- 코드 개발은 M5 담당 유지. `apps/m1-intranet`은 M1·M2 공통 게시판, `apps/m3-ott`는 OTT·AI, `apps/m5-store`는 Store로 구분합니다. 게시판 코드를 국가별로 복제하지 않습니다.
- M3·M5는 **GitHub Actions(CI: 빌드·검사) + Argo CD(CD: 배포)** 기본안을 사용합니다. 기존 K8s·EKS에서 Argo CD를 실행하며 별도 로컬 CI VM은 기본안에 추가하지 않습니다. 정적 S3 배포는 별도 경로입니다.
- GitHub는 계획서·WBS·회의록·팀 작성 설계·앱 코드를 간결하게 연결하고, 실제 설정·공격 증거는 Notion에 기록합니다. AI 제작 Topology는 공개 저장소에 올리지 않습니다.

### AS-IS 일정 예상 변경·기록 기준

- 10/20 공유: 실제 PC·VMware·UTM·망 간 연결 제약에 맞춰 설계를 검토하면서 AS-IS Topology는 **기존10/20 목표에서 10/21 오전 완료 예상**으로 변경 전망.
- 이는 실제 제출 완료·전원 합의로 확정한 마감이 아닙니다. 10/21 Topology·연결을 확인한 망부터 장비 생성·OS 설치를 시작하고 당일 진척을 기록합니다.
- 10/28 구축·이후 공격 목표는 잠정 유지하며 영향 확인 전 전체 일정을 일괄 하루 미루지 않습니다. 담당별 실제 소요를 확인한 뒤 조정합니다.
- WBS에는 기존 목표·현재 예상·사유·영향·확정 상태, Issue에는 본인 진행·막힌 점, Notion에는 기술 원인·설정/시험 근거를 남깁니다.
